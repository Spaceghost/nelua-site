neboot

A UEFI boot menu written in Nelua. It starts Cascadia with Theseus Init or OpenRC recovery from the same kernel and initramfs. A third entry starts another EFI application.

Boot in QEMU

On an x86-64 host with the Cascadia launcher, install tools/neboot-live from the neboot repository on your PATH. The build needs the Nelua fork, necc and its staged SDK, nelinker, make, Python 3, xorriso, sfdisk and mtools. QEMU uses x86-64 OVMF firmware.

cascadia-live --uefi

The launcher fetches neboot, prepares the latest Cascadia image, extracts the kernel and initramfs, and stages a temporary EFI disk as the user who runs it. At the serial menu, choose a key.

  • 1 boots Cascadia with Theseus Init as PID 1.
  • 2 boots Cascadia with OpenRC as PID 1 for recovery.
  • 3 runs the second EFI application. Control returns to the menu when it exits or the file is missing.
  • Q returns to firmware.

From Nelua to BOOTX64.EFI

  1. The Nelua fork emits freestanding C. Nelua records describe the firmware tables. Both the exported entry point and the function types stored in protocol records carry ms_abi, so the convention survives an indirect call through a record field.
  2. necc compiles the generated C to x86-64 ELF objects using its native backend. The SDK supplies TinyCC for preprocessing and assembly.
  3. nelinker reads those objects and writes a PE32+ EFI application. Its base relocation table tells the firmware which absolute addresses to adjust if the image moves.

For example, the console’s write function has type function<ms_abi>(pointer, *uint16): usize. Calling it passes the console and a pointer to UTF-16 text back to firmware.

Both Linux entries start the EFI stub in /boot/vmlinuz on the EFI System Partition and pass /boot/initramfs in the kernel’s load options. The chainload entry starts /EFI/TOOLS/second.efi from the same partition.

What ran under OVMF

On 21 November 2026, x86-64 QEMU with KVM and OVMF booted the image with Secure Boot disabled. The loader requested base 0x100000000. Firmware placed it at 0x3e2fb000 in both runs.

  • With the child application present, it printed a message and returned to the menu. Selecting Theseus then booted Linux with theseus-init as PID 1. An HTTPS request from the guest returned 200.
  • With the child file missing, the menu reported EFI_NOT_FOUND and appeared again. Selecting OpenRC recovery booted Linux with openrc-init as PID 1.

A separate calling-convention test used a GCC-built firmware shim to call the Nelua entry point. The entry point called the shim’s console function through a protocol pointer and returned 42 to the caller.
