Taking the address of Cosmopolitan 4.0.2’s strstr IFUNC failed in this toolchain; direct calls passed, so this measures the direct-call path and does not establish function-pointer ABI conformance. Loop, pointer-call and checksum overhead is included equally, not subtracted. Buffers are hot and aligned; this is not a DRAM bandwidth, cold-cache, multicore or application throughput result. The record parser is a synthetic combined workload; qsort includes initializing its input, and malloc/free includes writing the first and last byte.

What to optimize next

Start with measured losses in frequently used operations, retain the winning cases, and require correctness before promoting a faster path. This ordering reflects this corpus; it is not a claim about every application's CPU profile.

  1. memmove-overlap: glibc + Nelibc measured 0.64× baseline speed at 1,024 bytes. Keep this case in the comparison while testing short, long, aligned and unaligned inputs.
  2. memset: Cosmopolitan + Nelibc measured 0.75× baseline speed at 8 bytes. Keep this case in the comparison while testing short, long, aligned and unaligned inputs.
  3. memchr-absent: glibc + Nelibc measured 0.76× baseline speed at 128 bytes. Keep this case in the comparison while testing short, long, aligned and unaligned inputs.

Decimal range handling. In the separate aligned controls, current Nelibc parsed 1e9999 in 143.13 µs and 1e-9999 in 147.90 µs. Native glibc took 15.28 and 14.92 ns respectively. Both produced the expected binary64 result, end pointer and ERANGE. Compare decimal inputs at all five offsets.

Correctness first: investigate or document the newly failing corpus cases before promoting optimizations: musl / Zig: regression/sigprocmask-internal; Cosmopolitan: functional/popen.

Next evidence: application profiles to weight the cases; more CPUs and working-set sizes; allocator contention and I/O workloads. A single-host microbenchmark cannot establish a globally fastest libc.
